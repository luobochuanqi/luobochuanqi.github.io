## 1. PWA 的现状（2025–2026）

### 1.1 什么是 PWA

MDN 的定义：PWA 是"使用 web 平台技术构建、但能提供类似平台专属应用体验的应用"；它像网站一样跨平台，像原生应用一样可以安装到设备、离线/后台运行、与设备集成（来源：MDN《Progressive web apps》，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps ）。web.dev 对 PWA 的定义与此一致："使用现代 API 构建和增强的 web 应用，提供增强的能力、可靠性和可安装性"（来源：web.dev《Learn PWA》，https://web.dev/learn/pwa/ ）。

### 1.2 今天"构成一个 PWA"的技术要件

按 MDN 的《Making PWAs installable》（https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable ），一个 web 应用要被视为可安装的 PWA，需要：

1. **Web App Manifest**（必需）。manifest 是一个 JSON 文件，告诉浏览器应用如何显示与运行（名称、图标、启动 URL、显示模式等）。W3C 规范见《Web Application Manifest》（https://www.w3.org/TR/appmanifest/ ）。
   - Chromium 系浏览器（Chrome、Edge、Samsung Internet 等）要求 manifest 至少包含：`name` 或 `short_name`、192px 与 512px 两种 `icons`、`start_url`、`display`（和/或 `display_override`），且 `prefer_related_applications` 必须为 `false` 或不存在（来源：同 MDN 页面）。
2. **HTTPS**（或 localhost/127.0.0.1）。可安装 PWA 必须通过 `https` 提供，这比"安全上下文"的要求更严格（来源：同 MDN 页面）。
3. **Service Worker**（不是可安装的硬性要求，但是 PWA 的标志性能力）。Service Worker 是独立于页面运行的事件驱动脚本，可拦截网络请求、管理缓存，是实现离线与后台同步的基石（来源：W3C Service Worker 规范仓库，https://github.com/w3c/ServiceWorker ；MDN 说明"虽非可安装要求，但许多 PWA 用 Service Worker 提供离线体验"，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable ）。Service Worker 1 规范正在向 W3C Recommendation 推进（来源：同上仓库 README，https://github.com/w3c/ServiceWorker ）。

相关配套能力（MDN PWA Reference，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps ）：Cache Storage（离线缓存）、Background Sync / Periodic Background Sync（后台同步）、Badging API（图标角标）、Notifications API（系统级通知）、Web Share（与设备内其他应用共享）、Window Controls Overlay（桌面端去掉默认标题栏）等。

### 1.3 能力项目（Capabilities Project / Project Fugu）

- web.dev 的 Capabilities 板块指出："web 上虽有许多能力，但仍存在差距，这正是 web capabilities 项目的切入点"（来源：https://web.dev/learn/pwa/capabilities/ ）。
- 历史脉络：Chrome 时代的 Project Fizz 在 2017 年推出 Web Bluetooth（Chrome 56）、Web USB（Chrome 61）——"最早两个专为缩小 web 与原生应用差距而设计的 API"；Fizz 后来演变为 Project Fugu 与当前的 Capabilities 项目，并从 Google 单一公司扩展为包含 Microsoft、Intel 等的跨公司项目（来源：ChromeOS.dev《PWAs: Past, Present, Future》，2024-09-03，https://chromeos.dev/en/posts/pwas-past-present-future ）。
- 规模：从 Chromium 71 到 118，Capabilities 项目已推出**近 60 个新 API**，包括：
  - 硬件访问扩展：WebHID、Web Serial、Web NFC；
  - 更深的 OS 集成：File System Access、Contact Picker API、Web Share / Web Share Target；
  - 已安装 PWA 的能力扩展：Badging API、App Shortcuts、File Handler API（来源：同 ChromeOS.dev 文章）。
- 代表性成果：Photoshop 通过 WebAssembly（移植既有 C++ 代码）+ Origin Private File System 完整登陆 web（来源：ChromeOS.dev 同上；web.dev《Photoshop on the web》，https://web.dev/articles/ps-on-the-web ）。
- 未来方向——"高信任安全模型 / Isolated Web Apps"：web 的安全模型要求新能力对"随手点开链接"的场景安全，这挡住了部分系统级 API；Google 的出路是让应用打包（Signed Web Bundle）、隔离（独立 `isolated-app` 协议）、独立窗口运行，从而获得 Direct Sockets、Borderless Display、Controlled Frame 等高信任 API（来源：ChromeOS.dev 同上）。团队视角的含义：PWA 的能力上限仍在快速变化，且正在分化为"开放 web / 已安装 PWA / 高信任隔离应用"的信任谱系，Google 建议"默认选择能覆盖需求的最低信任级别以获得最大触达"（来源：同文章）。

### 1.4 各浏览器 / 厂商姿态

**可安装性（MDN 支持矩阵，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable ）**

| 平台 | 状态 |
|---|---|
| 桌面 Chromium（Chrome/Edge 等） | 所有受支持桌面系统均可安装带 manifest 的 PWA |
| 桌面 Safari | macOS Sonoma（Safari 17）起支持 File > Add to Dock，**有无 manifest 均可** |
| 桌面 Firefox | 不支持基于 manifest 的 PWA 安装 |
| Android | Firefox、Chrome、Edge、Opera、Samsung Internet 均支持安装 PWA |
| iOS ≤ 16.3 | 仅 Safari 可安装 |
| iOS ≥ 16.4 | 可从 Safari、Chrome、Edge、Firefox、Orion 的分享菜单安装 |

其他要点（同 MDN 页面 + ChromeOS.dev）：

- **iOS 16.4 是分水岭**：iOS 16.4+ 支持 Web Push（推送通知）与 Badging（角标）。Apple 官方文档要求：推送必须使用跨浏览器标准（Push API / Notifications API / Badging API / Service Worker），用户授予后需在 Service Worker 中**立即**展示通知，否则 Safari 会撤销该站点的推送权限；无需加入 Apple Developer Program 即可发送 web push；服务端需走 VAPID + RFC 8030，流量走 `https://*.push.apple.com`（APNs）（来源：Apple《Sending web push notifications in web apps and browsers》，https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers ；Apple WWDC23《What's new in web apps》视频，https://developer.apple.com/videos/play/wwdc2023/10120/ ）。注意：iOS 16.4 前，iPhone 上的 web 应用在推送上是"零能力"（来源：同上 Apple 文档的"iOS 16.4 or later"限定）。
- `beforeinstallprompt`（页内自定义安装按钮）在 **iOS 上不受支持**（来源：MDN 同页面）。
- Android 安装提示可展示 `description` 与 `screenshots` manifest 字段，**仅 Android**（来源：MDN 同页面）。
- Chrome 桌面/Android、Safari 桌面、Edge 桌面还允许把任意网站装成应用（无需满足 manifest 标准），但有 manifest 时浏览器才会主动推广安装（来源：MDN 同页面）。
- Microsoft Edge 官方文档同样强调 PWA 可提交到 Microsoft Store、支持推送/离线/定期后台更新、访问硬件，并主张"单一代码库跨 web/移动端/桌面"（来源：https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/ ）。
- 生态工具链：Lighthouse 可在 CI 中检验安装标准；Workbox 管理 Service Worker；Bubblewrap 与 PWA Builder 负责打包上架（来源：ChromeOS.dev 文章）。

### 1.5 需要标记的不确定点

- **关于"Google Play 于 2024 年 6 月弃用 PWA 上架（TWA / Digital Goods 通道）"的说法：未获一手证实。** 截至本文撰写，Google 官方文档仍把"把 PWA 列入 Google Play"描述为现行路径：ChromeOS.dev《List your Progressive Web App in Google Play》完整介绍 Bubblewrap 打包、Digital Asset Links、Play Billing 流程（https://chromeos.dev/en/publish/pwa-in-play ）；TWA（Trusted Web Activity）在 Android 官方文档中仍是受维护的协议（https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities ，页面更新日期 2026-02）。本报告未找到 Google 官方弃用公告。**建议：做决策前直接以 Google 文档现状为准，并在立项前复核该时间点。**
- ChromeOS.dev 文章的日期（2024-09-03）意味着其"近 60 个 API""Chromium 71–118"是截至 2024 年的口径，2025–2026 的具体数字会有更新（估算/过时风险，来源同上）。

## 3. PWA 的存在形式 / 安装方式

### 3.1 基本形态：web 交付物，不是 APK/IPA

PWA 的本质是"以网站形式分发、以应用形式安装"：开发者部署到 HTTPS 服务器，用户通过浏览器访问即可使用；满足安装标准后浏览器提供安装入口，安装后图标出现在主屏幕/任务栏，以独立窗口（`display: standalone`）运行，不再带浏览器 UI（来源：MDN《Making PWAs installable》，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable ）。与原生/Flutter 的关键区别：

- **无应用商店打包**：没有 APK/AAB/IPA 的构建-签名-提审流程（例外见 3.4 商店路径）；
- **更新随 web 发布即达**：用户下次访问/拉取即获得新版本，Service Worker 控制缓存策略；上架 Play 的 PWA 通常**无需**为功能更新重新提审，仅在应用超一年、manifest 变更等少数场景需要更新包（来源：ChromeOS.dev《List your PWA in Google Play》，https://chromeos.dev/en/publish/pwa-in-play ）；
- **离线靠 Service Worker 缓存**（Cache Storage），而非打包进安装包（来源：MDN PWA Reference，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps ）；
- **无下载体积门槛**：Twitter Lite 600KB vs 原生 23.5MB（来源：https://web.dev/case-studies/twitter ）。

### 3.2 三条主要安装路径

**(a) 浏览器安装提示（Install Prompt）**
- 桌面：Chromium 浏览器在所有受支持桌面系统支持；Safari（macOS Sonoma/Safari 17+）支持 Add to Dock；Firefox 不支持（来源：MDN 支持矩阵，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable ）。
- Android：Chrome/Edge/Firefox/Opera/Samsung Internet 均支持；满足 manifest + HTTPS 标准后，URL 栏出现安装图标，点击即安装；开发者还可用 `beforeinstallprompt` 事件触发页内安装按钮（iOS 不支持此事件）（来源：同 MDN 页面）。
- Edge 官方文档同口径：PWA 可"从应用商店安装，或借助支持型浏览器的应用安装功能安装"（来源：https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/ ）。
- 补充：Chrome 154（2026-08 发布说明）将允许网站通过声明式元素或 API 主动提示用户安装 web 应用（来源：Chrome Enterprise 发布说明，https://support.google.com/chrome/a/answer/10314655 ）。

**(b) 手动"添加到主屏幕"（Add to Home Screen / Add to Dock）**
- iOS：16.3 及以下仅 Safari 可装（分享菜单）；16.4+ 起 Safari、Chrome、Edge、Firefox、Orion 均可从分享菜单安装（来源：MDN 支持矩阵）。这是 iOS 上最主要的 PWA 安装方式；iOS 16.4+ 安装到主屏幕的 PWA 才能收到 Web Push（来源：Apple 文档，https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers ）。
- Android Chrome 菜单、Safari Add to Dock 同理（来源：MDN 同页面）。
- 注意：`<meta name="apple-itunes-app">` 那类"Smart App Banner"（把用户导向原生 App 的横幅）是更早期的机制，与 manifest 驱动的 PWA 安装是两回事，本报告不展开；iOS 的 Smart App Banner 仅限 Safari 常规浏览模式可用（来源：Apple Developer 论坛官方说明，https://developer.apple.com/forums/thread/71768 ）。

**(c) 应用商店路径**
- **Google Play（Android/ChromeOS）**：官方路径是用 Bubblewrap 把 PWA 打包成 Android App Bundle（底层是 TWA：全屏、无浏览器 UI 的 Custom Tab 协议）上架 Play，从而获得商店发现/评分/Play Billing；需要配置 Digital Asset Links 验证所有权；支持"ChromeOS-only PWA 与原生 Android 应用共用一个 listing"（来源：ChromeOS.dev《List your PWA in Google Play》，https://chromeos.dev/en/publish/pwa-in-play ；TWA 官方概览，https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities ）。数字商品销售须集成 Play Billing（来源：https://chromeos.dev/en/publish/pwa-play-billing ）。"Play 于 2024-06 弃用 PWA"的说法**未获一手证实**（见 1.5）。
- **Microsoft Store**：Edge 官方文档明确 PWA"与其他应用一样"可上架 Microsoft Store，用户全程无需打开浏览器；另支持通过 PWABuilder 等工具发布（来源：https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/ ；https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/how-to/microsoft-store ）。
- **Apple App Store：没有 PWA 上架路径。** MDN 列出的商店发布路径只有 Google Play、Microsoft Store、Meta Quest Store（PWABuilder 支持清单里出现 iOS 是工具能力描述，Apple 官方并未开放 PWA 直接上架 App Store）（来源：MDN《Making PWAs installable》，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable ）。iOS 侧 PWA 只能走"添加到主屏幕"，且功能面（推送仅限 iOS 16.4+ 主屏幕 PWA、无 `beforeinstallprompt`、通知必须即时展示等）仍明显弱于 Android 侧（来源：Apple 文档、MDN 支持矩阵，同上）。
- 其他：Meta Quest Store 也支持 PWA 上架（来源：MDN 同页面，链接 https://developers.meta.com/horizon/resources/publish-submit/ ）。

### 3.3 "安装"在各平台上意味着什么

- **Android（含 13+）**：安装后图标进入主屏幕，以独立窗口（standalone）启动，无浏览器 UI；已安装 PWA 可参与通知、角标（Badging）、App Shortcuts、文件关联（File Handler）等系统级集成（来源：MDN manifest `display` 说明；ChromeOS.dev 文章"已安装 PWA 的能力扩展"一节，https://chromeos.dev/en/posts/pwas-past-present-future ）。历史注记：早期 Android PWA 只是"主屏幕快捷方式"，自 2016 年 WebAPK 合并进 Chromium 后才获得真正的系统级集成（来源：ChromeOS.dev 同文章）。
- **iOS**："Add to Home Screen / Add to Dock"生成一个全屏运行的 web 应用图标，体验接近原生 App（无 Safari 栏）；iOS 16.4+ 支持推送与角标，且角标权限可在系统通知设置中单独配置（来源：Apple 文档，https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers ；MDN 支持矩阵）。
- **桌面**：独立窗口运行；`display: standalone` 表示无浏览器元素；`Window Controls Overlay` 可进一步隐藏默认标题栏、全表面渲染（来源：MDN，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable 与 https://developer.mozilla.org/en-US/docs/Web/API/Window_Controls_Overlay_API ）。

### 3.4 与原生 / Flutter 的安装流程对照

| 维度 | PWA | 原生 / Flutter |
|---|---|---|
| 交付物 | HTTPS 站点（+ manifest + SW），无安装包 | APK/AAB（Android）、IPA（iOS） |
| 分发 | 链接/搜索直达；商店为可选增强 | 商店为主分发渠道（iOS 必须） |
| 更新 | 随 web 发布即达，无审核（已上架 Play 的 PWA 也通常免更新提审，https://chromeos.dev/en/publish/pwa-in-play ） | 每次发版走商店审核 |
| 离线 | Service Worker 缓存，按需 | 资源打包在应用内 |
| 商店触达 | Play/MS Store 可选；**Apple App Store 无 PWA 路径**（MDN，见 3.2c） | 全量商店触达 |
| 下载摩擦 | 无下载；首访即可用（600KB 级，来源：https://web.dev/case-studies/twitter ） | 需下载安装包 |

## 4. 优劣对比与选型建议（中立）

### 4.1 三方案对比

| 维度 | PWA | 原生（iOS/Android 分开） | Flutter（跨平台编译） |
|---|---|---|---|
| 分发/安装摩擦 | 最低：链接即达、浏览器内安装、无审核 | 最高：商店打包+审核+下载 | 高：与原生相当 |
| 代码库数量 | 1 个（web/移动/桌面共用，https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/ ） | 2+ 个 | 1 个 |
| 离线能力 | 有（Service Worker 缓存，https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps ） | 完整 | 完整 |
| 推送通知 | Android 完整；**iOS 仅 16.4+ 主屏幕 PWA**，且通知必须即时展示（Apple 文档，见 3.2b） | 完整 | 完整（走原生推送） |
| 设备 API 覆盖 | 取决于浏览器标准：已有近 60 个新 API（Fugu/Capabilities，ChromeOS.dev 文章），但"drive-by web"安全模型挡住部分系统级能力；高信任 API 需 Isolated Web Apps（ChromeOS.dev 文章） | 完整 | 大部分（经插件桥接） |
| 性能上限 | Web 引擎性能；WebAssembly 可补计算密集型（Photoshop on web，https://web.dev/articles/ps-on-the-web ） | 最高 | 接近原生（Dart 编译为本地代码） |
| 商店触达/发现 | Play、MS Store 可选（Bubblewrap/TWA，https://chromeos.dev/en/publish/pwa-in-play ）；iOS 无商店路径 | 全量 | 全量 |
| 更新成本 | web 发布即达 | 商店审核周期 | 商店审核周期 |
| 弱网/低端机市场 | 有成功案例：Twitter Lite 600KB（https://web.dev/case-studies/twitter ）、Flipkart 2G 市场（https://web.dev/case-studies/flipkart ） | 依赖 Lite 版/优化 | 依赖 AOT 优化 |

### 4.2 决策时应权衡的因素（不作方向性推荐）

1. **iOS 占比与推送依赖度**。若核心用户在 iOS、且业务强依赖推送拉活，PWA 在 iOS 侧是显著短板（推送仅限 16.4+ 主屏幕 PWA、无商店、无 `beforeinstallprompt`；来源：Apple 文档、MDN 支持矩阵）；Android 侧则相反，PWA 体验最完整。
2. **设备/系统能力需求**。若需要系统级 API（深度硬件、系统服务、后台长任务），先对照 Capabilities 项目 API 清单（https://web.dev/learn/pwa/capabilities/ ）逐条核对"是否在标准里、是否在你最低支持的浏览器版本里"；Google 自身也建议"默认选最低信任级别，拿不到能力再升级"（ChromeOS.dev 文章）。注意该清单以 Chromium 进度为锚，Safari 跟进通常滞后（本报告未逐项验证 Safari 支持，需按目标 iOS 版本单独核对）。
3. **市场与网络条件**。弱网/低端机市场（Flipkart、Twitter Lite 场景）是 PWA 的优势区（web.dev 案例研究）；若目标市场网络条件好、用户习惯商店，商店分发优势减弱。
4. **迭代速度与成本**。PWA"更新随 web 发布"（ChromeOS.dev 商店页）、单一代码库（Edge 文档）适合快速迭代与多端复用；反过来，商店的审核、分发、收款（Play Billing / IAP 政策差异）是 PWA 无法复制或需要额外处理的。
5. **合规/收款政策差异**。PWA 上架 Play 时数字商品须走 Play Billing（https://chromeos.dev/en/publish/pwa-play-billing ）；iOS 侧 PWA 不走 IAP，收款路径与商店应用不同（依据：Apple 无 PWA 上架路径，MDN 3.2c；此为结构性推断，具体合规结论请法务确认）。
6. **能力上限的演化风险**。PWA 能力面仍在快速扩张（Isolated Web Apps 等，ChromeOS.dev 文章），选型时应把"18–24 个月后能力面是否覆盖核心场景"作为显式评估项，而非只看今天。
